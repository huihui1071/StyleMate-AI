# StyleMate Supply 面试准备

## 1. 面试时先讲什么

不要从技术栈开始，也不要把它介绍成“一个 AI 聊天机器人”。推荐顺序：

1. 谁在什么场景下遇到什么问题。
2. 为什么普通搜索或开放式大模型回答不够。
3. 你把业务流程拆成了哪些可验证步骤。
4. 现场演示一条完整链路。
5. 再解释架构选择、评估方式和下一步演进。

## 2. 30 秒版本

> StyleMate Supply 是一个面向服装供应商客户的智能选款台。网店商家用自然语言输入渠道、客群、价格带、目标款数和采购预算，系统先做结构化硬筛选，再按主销、引流、形象、连带和测试五种角色组货，最后生成可调整的采购清单。涉及实时库存、议价或锁货时，系统不会虚构执行，而是带着完整上下文转交销售。项目目前有 240 条匿名商品、真实商品图片、4 个商家画像，同时提供独立 Web 版和 Dify 编排版。

## 3. 1 分钟版本

> 我做这个项目是因为供应商选款不是简单的商品推荐。商家既有渠道、人群和价格带等硬约束，也需要控制首批预算、MOQ 和货品结构。如果直接让大模型推荐，它很容易放宽条件、编造库存，或者只给出几件看起来相似的商品。
>
> 我的方案把系统拆成四层。第一层将自然语言解析为结构化采购条件；第二层执行不可放宽的硬筛选；第三层根据风格、毛利、库存和风险排序，并按五种经营角色组货；第四层生成可调整的采购清单。真实库存、议价、账期和合同属于高风险动作，会生成销售接管摘要。
>
> 前端使用 React 和 TypeScript，决策服务使用 FastAPI。240 条商品和图片全部本地化，Web 版与 Dify 版复用同一个 API。项目通过规则测试、前端测试、生产构建和隐私扫描保证结果可验证。

## 4. 3–5 分钟项目讲述

### 4.1 背景与用户

> 用户不是最终消费者，而是从供应商货盘中选品的淘宝、抖音电商和小红书店铺商家。他们上新时要同时考虑客群、风格、价格、MOQ、库存风险和预算。供应商销售则要承担最后的价格确认、锁货和合同流程。

### 4.2 核心问题

> 这个场景有三个关键难点。第一，自然语言需要转成机器可以执行的条件；第二，推荐不只是单品相关性，而是整批货的结构和资金分配；第三，系统必须知道自己的权限边界，不能声称已经锁库存或完成下单。

### 4.3 方案

> 我把条件分成硬条件和软偏好。渠道、人群、品类、季节、价格带和 MOQ 是硬条件，任何一项不满足就不能进入候选。风格、毛利、库存、交期和风险用于候选集内排序。然后系统按五种经营角色选择商品，并把数量调整为 MOQ 的整数倍。如果超预算，先减少数量，再优先移除测试或形象类高成本商品。

### 4.4 架构

> React 工作台和 Dify Chatflow 都调用同一个 FastAPI 决策服务。FastAPI 内部依次处理意图路由、条件解析、硬筛选、排序、组货、预算校验和销售接管。数据层目前是 240 条匿名 JSON 商品、4 个商家画像和 240 张本地图片。部署使用一个多阶段 Docker 镜像，FastAPI 同域提供 API、SPA 和图片资源。

### 4.5 可信度

> 我没有把 Demo 模拟值伪装成真实业务数据。商品属性和图片经过匿名化，供货、库存和经营测算明确标记为模拟值。仓库有隐私扫描；测试覆盖无结果不放宽、MOQ、库存、预算、五类角色、商家差异和销售接管。

### 4.6 局限与下一步

> 当前 NLU 主要是规则词典和正则，因此可解释但语言覆盖有限；数据没有连接真实 ERP，也没有账号、数据库和持久化。生产版我会让大模型只负责生成结构化查询，并通过 Schema 校验，关键筛选和交易动作继续走确定性规则与人工审批。排序部分再使用真实采购、售罄和退货数据进行学习。

## 5. 推荐 Demo 路线

### 5.1 演示前准备

- 提前打开产品页与 `/demo`，避免免费服务唤醒影响节奏。
- 浏览器使用 100% 缩放，建议宽度 1280px 以上。
- 先展示产品首页，用一句话说明用户和价值，再进入工作台。
- 不要从代码开始，先让面试官看到完整业务闭环。

### 5.2 五分钟现场演示

#### 第一步：商家画像

选择“北岸通勤店”，说明系统已经知道渠道、目标客群、价格带和默认预算。

讲述重点：

> 同一句模糊需求放在不同商家画像下，候选结果会不同。画像不是展示标签，而是会参与有效约束和排序。

#### 第二步：完整组货

输入：

```text
我在淘宝做女性通勤装，零售价300-700元，想选12款春季新品，首批采购预算3万
```

展示：

- 识别出的渠道、人群、季节、价格带、预算和目标款数。
- 候选范围与 12 款组货结果。
- 五种经营角色。
- 每款的推荐理由、供货价、建议零售价、库存、MOQ 和交期。
- 采购清单中的总件数、采购额、预算余量和毛利空间。

讲述重点：

> 页面上的数字来自同一条决策链，采购金额可以由单价和数量复算，不是模型生成的一段营销文案。

#### 第三步：硬条件不放宽

输入一个难以命中的组合，例如：

```text
冬季紫色真丝套装，零售价200元以内
```

讲述重点：

> 当前货盘没有满足条件的商品时，系统返回空结果，不为了看起来智能而推荐不符合要求的商品。

#### 第四步：销售接管

输入：

```text
请联系销售确认这份选款单并锁库存
```

展示接管原因、负责人、上下文摘要和“未执行真实交易”的提示。

讲述重点：

> Agent 的能力不只是调用工具，也包括知道什么时候不能调用。锁货和价格承诺必须连接真实权限系统并经过审批。

#### 第五步：补充 Dify 版

简短打开 Dify 页面，说明它是第二种交互入口：

> Dify 负责对话流程和 Markdown 展示，核心决策仍调用同一个 FastAPI API，所以不会因为换了入口就产生另一套推荐逻辑。

## 6. 高频面试问题与参考回答

### Q1：这个项目的商业价值是什么？

**回答思路：**

它缩短了商家从表达需求到形成首批采购清单的路径。对商家，价值是减少筛货和计算成本、降低 MOQ 与预算风险；对供应商，价值是让销售从重复找款转向处理议价、库存和关系维护。生产环境应重点观察选款任务完成时长、推荐采纳率、转销售率、采购转化率、售罄率和退货率。

### Q2：为什么后来定位成供应商选款，而不是消费者导购？

**回答思路：**

原始能力可以支持消费者找商品，但数据形态和业务流程更适合供应商货盘。B2B 用户有更明确的渠道、MOQ、预算和组货诉求，也存在销售接管这一真实闭环。重新定位后，项目从“推荐几件衣服”变成“辅助完成一项采购任务”，产品价值和技术约束都更清晰。

### Q3：为什么不让大模型直接推荐？

**回答思路：**

这个场景的关键条件可被验证，错误放宽价格带或 MOQ 会直接影响采购风险。大模型适合理解语言和生成解释，但不应绕过结构化数据、库存和预算规则。当前 Demo 用规则解析获得可重复结果；生产版可以用大模型生成结构化查询，但必须经过 Schema 校验，并由确定性服务执行硬筛选和交易权限检查。

### Q4：没有使用 LLM，这还能叫 AI Agent 吗？

**回答思路：**

我不会把当前实现描述成自主通用 Agent。更准确的说法是“任务型智能选款系统”或“带业务边界的 AI 员工 Demo”。它具备自然语言入口、上下文、意图路由、决策步骤和人工接管，但核心决策是确定性的。这样做是有意的产品取舍：先验证流程和可靠性，再替换或增强理解模块，而不是为了使用 LLM 而牺牲可控性。

### Q5：自然语言解析是怎么做的？

**回答思路：**

`parse_query` 使用领域同义词表和正则表达式，把文本解析成 `ParsedQuery`。类别字段通过别名归一化，价格、预算、款数和 MOQ 通过正则提取。代码特别避免把“25到35岁”误识别为价格区间。解析结果会作为证据返回，便于调试和用户核对。

### Q6：规则解析的缺点是什么？

**回答思路：**

它对训练数据没有依赖、结果稳定且容易测试，但覆盖新表达的成本较高，对否定、比较、多轮省略和复杂条件的支持有限。生产化会采用混合方案：模型输出受约束的 JSON，Pydantic 做类型和范围校验，领域词典负责归一化，后端仍执行最终规则。

### Q7：硬筛选和排序为什么要分开？

**回答思路：**

硬筛选回答“能不能卖给这家店”，排序回答“在能卖的商品里哪个更合适”。如果把两者合成一个总分，高毛利商品可能用高分抵消价格带或渠道不匹配。分层后，硬条件永远不会被软特征覆盖，也更容易定位无结果的原因。

### Q8：商家画像如何影响结果？

**回答思路：**

用户没有显式输入时，系统继承商家画像中的人群、渠道和价格带作为有效约束；历史风格和偏好品类进入软评分；折扣系数影响结算单价；默认预算影响组货总额。测试会比较不同商家在同一查询下的候选 SKU，确保画像真正参与决策。

### Q9：组货算法是怎样的？

**回答思路：**

先把目标款数展开为五类经营角色。每种角色有不同的适配函数，例如引流款偏向价格带下沿和库存，形象款偏向风格表达和较高零售价，测试款允许更高风格风险。选择时优先使用不同 `style_code`，然后根据角色目标件数和 MOQ 计算数量，最后执行预算收缩。

### Q10：如何保证不超预算？

**回答思路：**

先计算商家折扣后的结算单价和行金额。超过预算时，优先选择可减少数量的商品，每次减少一个 MOQ；如果已经降到 MOQ 仍超预算，再移除测试款或形象款中的高成本商品。最终测试断言总采购额不超过预算，所有数量均为 MOQ 整数倍且不超过库存。

### Q11：为什么有五种经营角色？

**回答思路：**

因为一批货的目标不是单一的点击率或相似度。主销款承担规模，引流款覆盖价格下沿，形象款建立店铺表达，连带款提升组合购买，测试款控制探索成本。这是把商品推荐转成商品组合决策的关键抽象。

### Q12：推荐理由如何生成？

**回答思路：**

理由来自实际评分特征，例如命中用户风格、贴合商家历史风格、毛利空间达到阈值或库存充足。它们与加分逻辑一起生成，而不是在得到结果后再让模型编一段理由，因此可以追溯到具体规则。

### Q13：如何处理没有结果？

**回答思路：**

当前版本返回空结果并明确说明不会自动放宽。如果要提升体验，可以根据缺口生成澄清建议，例如询问用户是否愿意放宽颜色或 MOQ，但任何放宽都需要用户确认，并记录放宽前后的条件。

### Q14：Dify 在系统中负责什么？

**回答思路：**

Dify 是对话交互和编排层：开始节点收集商家画像，HTTP 节点调用 FastAPI，Code 节点把 JSON 整理为带图片和数字的 Markdown，Answer 节点输出。它不保存第二套选款逻辑，也没有让 LLM改写关键决策。

### Q15：为什么同时做独立 Web 版和 Dify 版？

**回答思路：**

独立 Web 版适合展示完整的 B2B 操作流程，例如三栏工作台、数量调整和采购清单；Dify 版验证同一能力能否以低代码对话渠道交付。两者共用 API，说明核心能力已经从界面中解耦。

### Q16：为什么采用单体而不是微服务？

**回答思路：**

当前规模只有一个前端、一个决策服务和静态数据，单服务部署降低了个人项目的运维成本，也避免跨域和多服务唤醒问题。代码内部已经按解析、筛选、排序和组货划分模块；当库存、订单、推荐和客户系统拥有独立扩展需求时，再拆服务更合理。

### Q17：为什么用 JSON 而不是数据库？

**回答思路：**

Demo 的商品规模固定、只读，JSON 可以降低环境依赖并让仓库开箱运行。但生产环境必须换成数据库和搜索索引，用于增量更新、并发、规则版本、租户隔离和审计。选择 JSON 是原型阶段的范围控制，不是长期架构判断。

### Q18：项目如何保证隐私？

**回答思路：**

所有公开标识都重新编号，图片下载到本地，仓库不保留源链接、真实品牌名、原始款号和客户信息。经营字段使用模拟值，并在界面明确标记。隐私扫描会检查禁用词、源款号形态、外部 URL 和不应提交的源文件。

### Q19：你如何评价这个系统？

**回答思路：**

当前是规则回归测试，重点验证约束满足率和业务不变量：不放宽硬条件、不超预算、数量符合 MOQ、角色结构完整、商家画像影响结果、交易请求必定接管。下一步会建立标注查询集，增加字段解析准确率、候选召回率、排序 NDCG、组货覆盖度和稳定性；上线后关注采纳率、任务时长、转人工率和实际售罄表现。

### Q20：如何防止大模型幻觉？

**回答思路：**

首先不让模型拥有商品事实和交易结果的最终决定权。商品字段只从数据源读取，硬条件、金额和权限由代码校验；输出只引用已有 SKU；交易请求返回“未执行”。如果接入 LLM，会增加结构化输出、字段白名单、检索结果约束、工具权限、幂等键、审批和审计日志。

### Q21：如果接入真实库存，架构如何变化？

**回答思路：**

静态库存字段会替换为库存服务查询。搜索阶段可以使用缓存库存做候选过滤，但在生成订单草稿或锁货前必须重新读取强一致库存。锁货接口要有幂等键、有效期和失败补偿，并且由登录用户授权或销售审批。

### Q22：如何支持两千条、十万条甚至更多商品？

**回答思路：**

240 条数据可以内存遍历；两千条仍可工作，但生产规模需要数据库索引或搜索引擎。结构化硬条件下推到 SQL/OpenSearch，软排序只处理候选集；图片使用对象存储和 CDN；热点画像与库存可缓存。计算密集的学习排序服务可以独立扩展。

### Q23：并发和性能瓶颈在哪里？

**回答思路：**

当前每次请求会遍历内存商品，复杂度近似 O(n)，240 条时不是瓶颈。规模扩大后，瓶颈会变成候选召回、库存实时查询和图片加载。需要索引、分页、缓存、异步 I/O、图片缩略图和 CDN，同时建立 P95 延迟与错误率监控。

### Q24：最难的产品决策是什么？

**回答思路：**

最难的是从“推荐商品”转为“完成采购任务”。这要求重做用户、信息结构和结果形式：加入商家画像、五类角色、建议件数、采购汇总和销售接管。它不是给旧页面换文案，而是重新定义系统的输入、决策和输出。

### Q25：最难的技术问题是什么？

**回答思路：**

一是区分硬约束与软偏好，避免高分商品绕过业务条件；二是在预算、MOQ、库存和角色结构之间得到可复算的组货结果；三是让 Web 和 Dify 两个入口复用同一个决策服务。可以结合 `_hard_match`、`_score` 和 `build_assortment` 三个函数讲代码。

### Q26：遇到过什么失败或返工？

**回答思路：**

早期方向偏向消费者导购，页面也有信息过多和海报式字体过大的问题。通过重新确认真实使用方，产品改为供应商智能选款；数据从少量 SKU 扩展到 240 条真实图片；前端从标签堆叠改成单向流程和三栏工作台；部署从前后端分散改为同域单服务。这个过程说明我不是只完成需求列表，而是在根据业务和真实体验修正产品假设。

### Q27：如果再给两周，你优先做什么？

**回答思路：**

第一优先是建立一套 50–100 条标注查询集，测量解析、约束满足和组货结构；第二是加入澄清问题，让不完整或冲突需求可以继续；第三是把数据迁移到 PostgreSQL 并增加规则配置；第四是把 Dify 工作流导出为 DSL 纳入版本控制。相比继续增加页面效果，这些工作更能提升系统可信度。

### Q28：你在项目中具体负责什么？

**回答思路：**

按自己的真实情况回答，不要笼统说“全部负责”。可以按以下结构：

> 我负责了产品定位、业务流程拆解、匿名数据建模、选款与组货规则、React 工作台、FastAPI 接口、Dify 编排、测试和 Render 部署。关键决策包括把硬筛选与软排序分离、把组货建模为五类角色、把交易请求转成销售接管，以及让两个交互入口复用同一个 API。

如果使用了 AI 编程工具，应主动说明：

## 8. 需要主动承认的局限

面试中不要回避以下问题：

- 当前不是基于真实交易数据训练的推荐模型。
- 当前自然语言解析不覆盖所有复杂表达。
- 库存、价格和经营指标是演示模拟值。
- 销售接管没有真正对接 CRM 或消息系统。
- 没有用户登录、租户隔离和清单持久化。
- 数据目前只覆盖春夏两季。
- 角色比例和权重需要业务数据校准。
- Dify DSL 尚未进入 Git 版本管理。

承认边界后马上补充“为什么当前这样取舍”和“生产版如何演进”，会比回避更有说服力。

## 10. 面试结束时的总结

> 这个项目最核心的价值不是生成了多少商品卡，而是把一个模糊的 B2B 选款需求变成了可执行、可解释、可测试的决策流程。我保留了 AI 擅长的自然语言入口，同时把价格、MOQ、预算和权限放在确定性规则中。当前 Demo 已经验证了完整闭环，下一步重点是接入真实系统、建立标注评测集，并用业务结果校准排序和组货策略。
